## 0. Problem Statement

M4 engine works correctly, but seed data has a severe calorie ceiling problem. The highest `cached_calories_per_serving` in the lunch pool is **575 kcal** (only 7 recipes ≥ 400), and **dinner's maximum is 391 kcal** (zero recipes ≥ 400). For any user with `target_calories ≥ 1600`, the engine's calorie window (`slot_target × 0.75–1.25`) finds **zero or near-zero** dinner candidates and very few lunch candidates.

**This means:** a 2000 kcal user wanting a normal lunch (800 kcal slot target, window 600–1000) finds **zero** lunch recipes. A 1600 kcal user wanting dinner (560 kcal slot target, window 420–700) finds **zero** dinner recipes. The engine raises `NoSuitableRecipeError` for the majority of realistic Indian adults.

**Root cause:** Most existing recipes are single-dish sabzis, dals, and salads (100–350 kcal/serving). Indian meals in the 400–650 kcal range are typically **composite meals** — rice + dal + sabzi, paratha + curry, biryani, thali plates — that we haven't seeded.

### 3.2 Raw vs Cooked Weight Discrepancy

> [!IMPORTANT]
> **Critical calibration issue**: Our recipes compute nutrition from **per-100g RAW weight** ingredients (IFCT/USDA raw basis), summing `ingredient.per_100g_nutrition × quantity_grams / 100`. Anuvaad's per-100g values are likely **per-100g COOKED/PREPARED weight** (the food as eaten).
>
> **Why this matters**: 100g raw rice → ~240g cooked rice. So our "per-100g" is per-100g-raw (dense), while Anuvaad's is per-100g-cooked (diluted). This explains why our kcal/100g is systematically **higher** than Anuvaad's for rice/dal-heavy dishes.

**Handling strategy for M4.5:**

1. **DO NOT calibrate ingredient quantities to match Anuvaad per-100g values** — this would undercount calories
2. **Instead, calibrate to Anuvaad's per-serving values** — these represent realistic portion sizes
3. **The target is `cached_calories_per_serving`**, which is already per-serving (total raw nutrition ÷ servings)
4. **Gemini prompt instruction**: "Target the per-serving calorie value. Calibrate ingredient quantities so that `total_raw_nutrition / servings` hits the kcal/serving target, not per-100g."
5. **Cross-reference**: After generation, compare our `cached_calories_per_serving` against Anuvaad's `unit_serving_energy_kcal` — these should be within ~30%, accounting for recipe variation

## 8. Execution Workflow

### Step 1: Gemini Recipe Generation

1. Open a fresh Gemini chat
2. Paste the **system prompt** from M3.5 `seed_expansion_plan.md` §8.1 with the **additional rules** from §4 above
3. Paste the **ingredient allowlist** — the 136 `app_id` values from `apps/recipes/seed_data/ingredients.json`, grouped by category (same as Appendix A of `seed_expansion_plan.md`)
4. Paste the **user prompt** from §4 (15 heavy-portion recipes with specific quantity guidance)
5. Gemini returns a single JSON array of 15 recipe objects

### Step 2: Claude Validation

1. Open a separate Claude chat
2. Paste the validation rules from §5 (standard M3.5 rules + M4.5-specific calorie target validation)
3. Paste Gemini's JSON output
4. Claude validates:
   - `ingredient_app_id` correctness — every ID exists in `ingredients.json`
   - `diet_tags` consistency — no chicken recipe tagged `vegetarian`, etc.
   - `allergen_tags` accuracy — eggs → `allergen_tags: ["eggs"]`, fish → `["fish"]`, etc.
   - `protein_source` accuracy — matches actual primary protein ingredient
   - `slug` uniqueness — no collision with existing 136 slugs
   - `quantity_grams` sanity — no 0g ingredients, no 2kg single ingredient, realistic portions
   - Instruction quality — 4–8 steps, logical order, no phantom ingredients

### Step 3: Fix and Re-validate

1. **PASSED** recipes → proceed to Step 4
2. **FAILED** recipes → report back with specific failure reasons
3. Fix in Gemini (re-prompt with corrections) and re-validate in Claude
4. Repeat until all 15 (or maximum passing set) are validated

### Step 4: Integration (Claude Code prompt)

Send a single Claude Code prompt to do all of the following atomically:

1. **Save batch file**: Write validated JSON to `apps/recipes/seed_data/sources/gemini_batches/batch_6_heavy_portion.json`
2. **Merge into recipes.json**: Append batch_6 recipes to `apps/recipes/seed_data/recipes.json`
3. **Apply 5 quantity fixes** (§6.3): Update ingredient quantities for Lemon Rice, Curd Rice, Panchmel Dal, Prawn Curry, and Rohu Machher Jhol in `recipes.json`
4. **Run seed**: `make seed` — verify no calorie warnings, all recipes load
5. **Verify calorie targets**: Each new recipe's `cached_calories_per_serving` is 400–650. Each fixed recipe hits its new target ±30%
6. **Run tests**: `make test` — all pass, update `test_engine_thin_cell_inventory` constants if needed
7. **Update BUILD_REPORT**: Add M4.5 section to `apps/recipes/seed_data/BUILD_REPORT.md` with new counts
8. **Single commit**: `feat(M4.5): heavy-portion seed expansion + existing recipe calibration`
9. **Push**: Together with M4 if not yet pushed, or as standalone commit

### Step 5: Post-Integration Verification

1. Manually verify gap zone analysis (§1.2) is resolved — re-run the same Django shell query
2. Confirm: dinner now has ≥4 recipes in the 400–650 range
