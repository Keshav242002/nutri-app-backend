# M4.6 — Weekly Batch Generation + Grocery List

**Author:** Antigravity Agent
**Date:** 2026-05-26
**Prerequisite:** M4 shipped (recommendation engine + single-day plans), M4.5 shipped (heavy-portion seed expansion)
**Blocks:** Usable meal planning product. Without weekly view + grocery list, the app cannot be used for real meal prep.
**Build sequence:** M4 → M4.5 → **M4.6** → M5 (tracker)

---

## 0. Problem Statement

The current product shows users **today's meal plan only**. This is insufficient for actual meal planning:

1. **No weekly view**: Users need to see Mon–Sun at a glance to decide if the plan works for their week
2. **No grocery list**: Without a shopping list, users can't prep. They'd have to manually read each recipe, note down ingredients, aggregate quantities, and figure out what to buy — nobody does this
3. **No batch generation**: Plans are generated lazily per-day (`get_or_generate_plan`). There's no "generate my whole week" action

**Without M4.6, the app is a recipe viewer, not a meal planner.**

## 1. Product Rules

### 1.1 Plan Generation Rules

| Rule | Detail |
|---|---|
| **First-time user (mid-week install)** | First plan covers **today through upcoming Sunday** (partial week, 1–7 days) |
| **All subsequent plans** | Cover **Monday through Sunday** (full ISO week) |
| **Generation trigger** | On-demand: user taps "Generate this week's plan". NOT cron-driven (cron is M6) |
| **Idempotency** | If plans already exist for days in range, keep them. Only generate missing days |
| **Atomicity** | If any day fails (`NoSuitableRecipeError`), roll back the entire batch — no partial weeks |
| **Regeneration** | Uses existing `regenerate_plan` / `regenerate_slot` from M4. No new regen logic |

### 1.2 Grocery List Rules

| Rule | Detail |
|---|---|
| **Computation trigger** | Lazy: computed when user requests it, not on plan generation |
| **Cache lifetime** | 7 days or until next plan generation/regeneration — whichever comes first |
| **Invalidation** | Any `regenerate_slot` or `regenerate_plan` call invalidates the cached grocery list for that week |
| **Grouping** | Ingredients grouped by `ingredient.category` for shopping efficiency |
| **Display quantities** | User-friendly: "1 kg rice" not "473.5g rice". Rounded up to practical retail units |
| **Household scaling** | Quantities scaled by `profile.household_size / recipe.servings` (e.g., household=4, servings=2 → 2× ingredients). Resolved: Option A |
| **Cost estimate** | Total estimated cost = Σ(`ingredient.approximate_price_inr_per_kg × quantity_kg`). Only for ingredients with `approximate_price_inr_per_kg` set |

### 2.4 Why `items` as JSONField (not normalized rows)

**Options considered:**

| Approach | Pros | Cons |
|---|---|---|
| `GroceryItem` FKs (one row per ingredient per week) | Relational purity, queryable per-item | ~40 rows per list × N users = row explosion; complex aggregation queries; need joins to get category display |
| `items` as JSONField (chosen) | Single row per user-week; pre-aggregated; fast read; easy cache invalidation (delete row) | Not queryable per-item at DB level; but we never need to query "all users buying rice this week" |

**Decision:** JSONField. The grocery list is a **read-heavy, write-once, user-scoped document**. Pre-computing it as structured JSON matches the access pattern perfectly. The UI will render it directly from the JSON.

## 3. Services

### 3.1 `apps/mealplans/services/weekly_service.py`

```python
def generate_weekly_plan(user: User, reference_date: date | None = None) -> list[MealPlan]:
    """Generate meal plans for the current (or specified) week.

    First-time mid-week: today → Sunday.
    All other cases: Monday → Sunday.

    - Skips days that already have a MealPlan (idempotent).
    - Atomic: if any day fails, rollback all newly created plans.
    - Invalidates cached grocery list for this week.

    Returns list of all MealPlan objects for the week (existing + newly created).
    """
```

**Algorithm:**

1. Determine `start_date` and `end_date`:
   ```python
   today = reference_date or date.today()
   has_any_plan = MealPlan.objects.filter(user=user).exists()
   if not has_any_plan:
       # First-time user: today → Sunday
       start_date = today
       end_date = today + timedelta(days=(6 - today.weekday()))
   else:
       # Returning user: Monday → Sunday of current week
       start_date = today - timedelta(days=today.weekday())
       end_date = start_date + timedelta(days=6)
   ```

2. Find existing plans in range:
   ```python
   existing = {
       p.plan_date: p
       for p in MealPlan.objects.filter(
           user=user, plan_date__range=(start_date, end_date)
       ).select_related("breakfast", "lunch", "dinner")
   }
   ```

3. Generate missing days inside `transaction.atomic()`:
   ```python
   with transaction.atomic():
       new_plans = []
       for day_offset in range((end_date - start_date).days + 1):
           plan_date = start_date + timedelta(days=day_offset)
           if plan_date in existing:
               continue  # idempotent: skip existing
           plan = get_or_generate_plan(user, plan_date)
           new_plans.append(plan)
       # If we get here, all days succeeded
   ```

4. Invalidate cached grocery list:
   ```python
   week_monday = start_date - timedelta(days=start_date.weekday())
   GroceryList.objects.filter(user=user, week_start_date=week_monday).delete()
   ```

5. Return all plans for the week (existing + new), ordered by date.

**Error handling:** If `get_or_generate_plan` raises `NoSuitableRecipeError` for any day, the `transaction.atomic()` block rolls back all newly created plans. The error propagates to the view layer.

### 3.2 `apps/mealplans/services/grocery_service.py`

```python
def get_or_compute_grocery_list(user: User, week_start_date: date) -> GroceryList:
    """Return cached GroceryList or compute and persist a new one."""
```

**Algorithm:**

1. Try to fetch cached:
   ```python
   try:
       return GroceryList.objects.get(user=user, week_start_date=week_start_date)
   except GroceryList.DoesNotExist:
       pass
   ```

2. Load all MealPlan rows for the week:
   ```python
   week_end = week_start_date + timedelta(days=6)
   plans = MealPlan.objects.filter(
       user=user,
       plan_date__range=(week_start_date, week_end),
   ).select_related("breakfast", "lunch", "dinner")
   ```

3. Collect all Recipe IDs across all slots:
   ```python
   recipe_ids: set[int] = set()
   for plan in plans:
       for slot in ("breakfast", "lunch", "dinner"):
           recipe = getattr(plan, slot)
           if recipe is not None:
               recipe_ids.add(recipe.id)
   ```

4. Query all RecipeIngredients for those recipes, grouped by ingredient:
   ```python
   from apps.recipes.models import RecipeIngredient
   from collections import defaultdict

   # ingredient_app_id → total_grams (summed across all recipe usages in the week)
   ingredient_totals: dict[str, float] = defaultdict(float)
   recipe_counts: dict[str, int] = defaultdict(int)

   ris = RecipeIngredient.objects.filter(
       recipe_id__in=recipe_ids
   ).select_related("ingredient")

   # Count how many times each recipe appears in the week
   recipe_usage_count: dict[int, int] = defaultdict(int)
   for plan in plans:
       for slot in ("breakfast", "lunch", "dinner"):
           recipe = getattr(plan, slot)
           if recipe is not None:
               recipe_usage_count[recipe.id] += 1

   for ri in ris:
       app_id = ri.ingredient.app_id
       # Q1 Resolution: Scale by household_size / recipe.servings
       # household_size=4, recipe.servings=2 → 2× ingredients (cook 2 batches)
       usage_count = recipe_usage_count.get(ri.recipe_id, 1)
       recipe_servings = ri.recipe.servings or 1  # guard against null/zero
       household_size = max(profile.household_size, 1)
       scaling_factor = household_size / recipe_servings
       # quantity_grams is for the full batch (recipe.servings portions)
       scaled_grams = float(ri.quantity_grams) * scaling_factor * usage_count
       ingredient_totals[app_id] += scaled_grams
       recipe_counts[app_id] += usage_count
   ```

5. Round to retail units:
   ```python
   for app_id, total_grams in ingredient_totals.items():
       ingredient = ingredients_by_app_id[app_id]
       display_qty, display_unit = _round_to_retail_unit(
           total_grams, ingredient.category
       )
   ```

6. Group by category, compute costs, build JSON, persist.

**Display formatting:**

```python
def _format_display_quantity(grams: float, round_to: float, unit: str) -> tuple[float, str]:
    """Round up to retail unit and format for display."""
    import math
    rounded_grams = math.ceil(grams / round_to) * round_to

    if unit == "pcs":
        # For eggs: convert grams to count (1 egg ≈ 50g)
        count = math.ceil(grams / 50.0)
        return (count, "pcs")

    if rounded_grams >= 1000:
        return (rounded_grams / 1000, "kg")
    else:
        return (rounded_grams, unit)
```

## 5. Endpoints

### `POST /api/v1/mealplans/week/generate/`

- **Auth:** Required
- **Body:** `{date: "2026-05-26"}` (optional — defaults to today)
- **Logic:** `generate_weekly_plan(request.user, parsed_date)`
- **Response:** Standard envelope with list of MealPlan objects for the week (using `MealPlanSerializer`)
- **Response shape:**
  ```json
  {
    "status": "success",
    "message": "Weekly meal plan generated (Mon 2026-05-25 to Sun 2026-05-31).",
    "data": {
      "week_start": "2026-05-25",
      "week_end": "2026-05-31",
      "days_generated": 5,
      "days_existing": 2,
      "plans": [...]
    }
  }
  ```
- **Errors:**
  - 422 `NO_SUITABLE_RECIPE` if engine can't find recipes for any day (entire batch rolled back)
  - 404 `PROFILE_NOT_FOUND` if user has no profile

### `GET /api/v1/mealplans/week/<date>/grocery/`

- **Auth:** Required
- **URL param:** `<date>` is any date in the target week (resolved to Monday)
- **Logic:** `get_or_compute_grocery_list(request.user, resolved_monday)`
- **Response:** Standard envelope with `GroceryListSerializer` output
- **Errors:**
  - 404 `MEAL_PLAN_NOT_FOUND` if no plans exist for that week (can't compute grocery list from nothing)
  - 404 `PROFILE_NOT_FOUND` if no profile (needed for `household_size`)

### `POST /api/v1/mealplans/week/<date>/grocery/regenerate/`

- **Auth:** Required
- **Logic:** Delete cached `GroceryList` for this week, recompute fresh
- **Use case:** After user swaps a slot, they tap "refresh grocery list"
- **Response:** Same as GET grocery endpoint

## 9. Open Questions

1. **Household scaling model**: Recipe `servings=2` means the recipe makes 2 portions. For `household_size=4`, should the grocery list assume:
   - **(A)** 4 people eat the same meal → multiply all quantities by `household_size / recipe.servings` (i.e., 4/2 = 2× more ingredients)
   - **(B)** Each person gets 1 serving → multiply by `household_size` (4×)
   - **(C)** Recipe already serves `servings` people, so multiply by `household_size / servings` only if `household_size > servings`
   
   **Recommendation:** Option A. `household_size=4, recipe.servings=2` → buy 2× more ingredients (cook 2 batches of the recipe). This matches how Indian households cook: you scale the recipe to feed everyone.

2. **Duplicate recipe handling**: If the engine picks the same recipe for Monday lunch and Thursday lunch, should the grocery list count its ingredients once (since you could batch-cook) or twice (since you might cook fresh each time)?
   
   **Recommendation:** Count twice. Freshness matters for Indian cooking. Batch-cooking optimization is a v2 feature.

3. **Spice pantry assumption**: Should very small quantities of pantry staples (salt, turmeric, red chilli powder — amounts < 25g for the whole week) be omitted from the grocery list with a note "Assumed available in your kitchen pantry"?
   
   **Recommendation:** Include them but mark with `"pantry_staple": true`. Let the UI decide whether to hide them (with a toggle "Show pantry staples").

4. **Week boundary**: If a user generates a plan on Saturday, should `generate_weekly_plan` generate Sat–Sun only (partial current week) or Mon–Sun of next week? 
   
   **Recommendation:** For first-time users, generate today→Sunday. For returning users who already have plans in the current week, generate the full current week (fill missing days). If the current week is already fully planned, do nothing (return existing plans). The user can advance to next week via the date parameter.

5. **Grocery list scope for partial weeks**: If a first-time user installs on Friday and gets a Fri–Sun plan (3 days), should the grocery list cover only those 3 days or round up to buy for a full week?
   
   **Recommendation:** Cover only the days with actual plans (3 days). The `summary.days_covered` field tells the UI how many days are included.

## 9.1 Resolved Decisions

> **Status: ALL QUESTIONS RESOLVED — Plan approved for implementation.**

| # | Question | Resolution |
|---|---|---|
| Q1 | **Household scaling model** | **Option A.** `household_size=4, recipe.servings=2` → buy 2× ingredients (`household_size / recipe.servings`). Scale recipe to feed everyone. |
| Q2 | **Duplicate recipe handling** | **Count twice.** If the engine picks the same recipe for Monday lunch and Thursday lunch, ingredients are summed for both occurrences. Do NOT optimize for batch cooking in v1. |
| Q3 | **Spice pantry assumption** | **Include all items** but mark pantry staples with `"pantry_staple": true` in the item JSON. UI decides whether to show/hide them. |
| Q4 | **Week boundary** | **First-time user** = generate today → Sunday (partial week). **Returning user** = current ISO week Monday → Sunday (fill gaps for any missing days). **All days already planned** = return existing plans unchanged. User can advance to next week via the `date` parameter. |
| Q5 | **Partial week grocery scope** | **Cover only planned days.** If a first-time user installs Friday and gets Fri–Sun (3 days), grocery list covers those 3 days only. `summary.days_covered` tells the UI how many days are included. |

### Implementation impact of resolutions

- **Q1 → `grocery_service.py`**: Scaling formula is `quantity_grams × (household_size / recipe.servings) × usage_count`. Update §3.2 step 4 accordingly.
- **Q2 → `grocery_service.py`**: `recipe_usage_count` already counts per-recipe appearances. No change needed — the algorithm in §3.2 already counts twice.
- **Q3 → Item JSON schema**: Add `"pantry_staple": true/false` field to each item in the `items` JSONField (§2.2). Pantry staple detection: `category == "spice"` AND `total_grams < 50` for the week, OR ingredient is in a hardcoded `PANTRY_STAPLES` set (salt, turmeric, red chilli powder, black pepper, cumin seeds, mustard seeds).
- **Q4 → `weekly_service.py`**: Already matches algorithm in §3.1. No changes.
- **Q5 → `grocery_service.py`**: Already matches algorithm in §3.2. `summary.days_covered` is set from actual plan count.

## 13. Risk Assessment

| Risk | Severity | Mitigation |
|---|---|---|
| `generate_weekly_plan` timeout for 7 days × 3 slots = 21 `select_recipe` calls | Low | Each call is <50ms (indexed queries + in-memory scoring). 21 calls ≈ 1s total. No concern for sync endpoint |
| Atomic rollback leaves user with no plans | Medium | Return clear error message: "Could not find suitable recipes for [slot] on [date]. Please adjust your dietary preferences." UI can offer fallback options |
| Grocery list invalidation race condition (user regens slot while grocery is being computed) | Low | Invalidation is a simple DELETE; worst case is stale list for one request. Next request recomputes |
| `household_size` changes mid-week | Low | Grocery list is ephemeral (re-computed on demand). Profile change → next grocery request gets updated quantities |
| Price data coverage is incomplete | Medium | `cost_coverage_pct` in summary tells user what % of items have price data. "Estimated cost" label in UI, not "Exact cost" |
| Very large household (size=12) generates unrealistic quantities | Low | `_round_to_retail_unit` handles large quantities correctly (2100g → 2.5 kg). Max household_size is 12 (validated in DietaryProfile) |
